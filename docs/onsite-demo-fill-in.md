# NIS 现场演示 · 逐字段填写内容（侦察员 → 执行员）

> 用途：验收现场照此输入，5–6 分钟走完 OODA 闭环，并顺带演示 AI 与审计。
> 环境：`http://192.168.58.20`（内网终端）或 `http://192.168.146.10`（外网口）。
> 场景：课程演示环境中的「目标区域活动规律核查」，**虚构数据，不对应任何真实目标**。

---

## 0. 人员与账号

| 演示人 | 账号 | 角色 | 机器 | 负责环节 |
|---|---|---|---|---|
| C | `recon01` | 侦察员 | C 的电脑 | Observe 侦察 |
| B | `analyst01` | 分析员 | B 的电脑 | Orient 分析 |
| D | `dmaker01` | 决策员 | D 的电脑 | Decide 决策 |
| A | `exec01` | 执行员 | A 的电脑（浏览器） | Act 执行 |
| （可选）| `admin` | 系统管理员 | 任意 | 审计 / 系统管理 |

**开始前 30 秒**：四台浏览器各登录自己的账号；A 确认 Windows 上 Ollama 在运行（托盘图标），否则 AI 会回退规则模板。

**先按 Ctrl + F5 强刷每个页面**：系统最近更新过前端，浏览器缓存旧包会看不到新按钮（如任务转交）。

### 0.5 开场自检（可选，约 1 分钟，很加分）

在 Ubuntu 的 `~/NIS` 下跑两条命令，用输出证明「环境健康 + 功能可跑 + 无高危漏洞」：

```bash
export NIS_DEMO_PASSWORD='***' NIS_ADMIN_PASSWORD='***'

# ① 功能体检：29 项断言
NIS_BASE_URL=http://127.0.0.1/api/v1 python3 scripts/smoke_features.py

# ② 按本演示脚本演练 + 安全检查：36 项断言
python3 scripts/audit_demo_and_security.py
```

预期输出：

```text
汇总：29 项检查，PASS 29 / FAIL 0
汇总：36 项，PASS 36 / FAIL 0（高危 0）
```

> 若被问「这是不是假的」，可以现场改一个权限或跑一次 curl 复现；两个脚本都支持反复执行。

## 1. 侦察（C / recon01，约 60 秒）

进入「侦察工作台」→ 点「新建侦察记录」（或工作台右上角新建按钮）。

| 字段（界面标签） | 填写内容（复制粘贴） |
|---|---|
| 标题 | `北侧路段车辆往返观察（08:00 时段）` |
| 来源类型 | `公开来源` |
| 来源说明 | `演示用公开素材，已脱敏` |
| 正文 | `在课程授权的演示环境中，观察点位于目标区域北侧路段。连续三日记录显示，每日 08:00 前后有车辆往返通过，路线固定、间隔稳定；伴随人员上下车与短暂停留（约 5 分钟）。以上内容为演示数据，不对应任何真实目标。` |
| 可信度 | `中` |
| 优先级 | `紧急`（演示置顶与标红；想低调可选「普通」） |

**AI 演示（15 秒）**：不点保存，直接点「**请求 AI 建议**」。

- 页面会提示"会自动保存草稿"，约 3–6 秒后出现建议；
- 念一句：**"建议里的时间和路线，就是从这条记录正文里归纳的，模型看不到其他数据。"**
- 点「**接受**」→ 状态变为「已接受」；再点一次会提示已处理（409）。

**提交**：点「提交记录」→ 选择分析员 `分析员甲（analyst01）` → 确认。

预期：记录状态 `已提交`，B 的待办里出现该记录。

## 2. 分析（B / analyst01，约 60 秒）

进入「分析工作台」→ 待办里打开刚才那条侦察记录 → 点「编写分析报告」。

| 字段 | 填写内容 |
|---|---|
| 标题 | `北侧路段活动规律分析（固定保障节点）` |
| 关联侦察记录 | 勾选 `北侧路段车辆往返观察（08:00 时段）` |
| 关键发现 | `北侧路段车辆往返时段与路线均稳定，08:00 前后为固定保障节点；人员与车辆在同一时段出现，存在时间耦合。` |
| 关联关系 | `车辆往返与人员上下车在同一时段出现；南北两侧道路的通行情况需要对比确认。` |
| 风险等级 | `中` |
| 建议措施 | `在固定时段前完成观察点部署，保留影像与通联记录，避免主动接触。` |
| 优先级 | `普通` |

**AI 演示（可选，15 秒）**：点「请求 AI 建议」→ 接受。念一句："这次建议引用的是报告的**关键发现**和**建议措施**原文。"

**提交**：点「提交给决策员」→ 选择 `决策员甲（dmaker01）` → 勾选「已确认 AI 内容」→ 确认。

预期：报告状态 `已提交待研判`；D 的工作台出现该报告。

## 3. 决策（D / dmaker01，约 60 秒）

进入「决策工作台」→ 打开「已提交待研判」的 `北侧路段活动规律分析（固定保障节点）` → 点「下达指令」/新建指令。

| 字段 | 填写内容 |
|---|---|
| 依据报告 | `北侧路段活动规律分析（固定保障节点）` |
| 标题 | `北侧路段核查与反馈（固定时段）` |
| 目标 | `确认北侧路段固定时段的车辆往返频次` |
| 正文 | `按约定时段到位观察，记录车辆往返频次、停留时长与人员活动；只做观察与记录，不主动接触；完成后提交结果与证据。` |
| 优先级 | `紧急`（演示置顶；也可普通） |
| 截止时间 | 今天 `+2 小时`（或当天 12:00） |

**冲突检查**：点「冲突检查」。

- 无冲突 → 直接进入下达；
- 若提示存在活动指令冲突 → 勾选「已确认冲突并继续」再下达（演示时可解释"系统阻止了重复下达，需要人工确认"）。

**下达**：选择执行员 `执行员甲（exec01）` → 确认下达。

预期：报告状态变 `已决策`；指令总体状态 `issued`；A 的待办里出现该指令（状态「待接收」）。

## 4. 执行（A / exec01，约 60 秒）

进入「执行工作台」→ 点开那条「待接收」的指令。

1. 点「**接收**」→ 状态「已接收」，接收时间写入；
2. 点「**开始执行**」→ 状态「执行中」；
3. 点「**填写结果并提交**」，填写下表：

| 字段 | 填写内容 |
|---|---|
| 结论 | `成功` |
| 结果摘要 | `按计划完成北侧路段 08:00 时段观察，取得 2 段连续记录。` |
| 过程与异常 | `观察期间记录车辆往返 3 次、人员上下车 2 次；未发生异常接触；影像与通联记录已存档。` |
| 证据 | 可跳过（当前契约只保存证据元数据，不上传二进制） |

4. 点「**提交结果**」。

预期：个人分配状态 `completed`；D 的指令总体状态变 `completed`。

## 6. 可选加分演示（各 20–30 秒）

### 6.1 任务转交（A / exec01）

**要求**：该指令处于「待接收 / 已接收 / 执行中」状态（已完成、已拒绝、已取消不能转交）。

操作路径：

```text
执行工作台 → 点开一条待接收/已接收的任务 → 详情底部「转交任务」按钮
→ 接收人下拉选「执行员乙（exec02）」（候选来自 /candidates，不含自己和已持有者）
→ 转交说明填「本人临时外出，转交同组执行员」→ 点「确认转交」
```

- 确认后：A 的待办消失（旧分配变「已取消」），exec02 登录后待办出现同一任务，内容（标题/正文）不变；
- 想演示「非法转交」：转给已完成的任务 → 409；转给自己 → 400。

> 页面看不到「转交任务」按钮：先 Ctrl+F5 强刷；仍没有说明浏览器还在用旧包。

### 6.2 细粒度权限（admin）

审计工作台 → 顶部切到「**系统管理**」→ 角色权限 → 选中「分析员」→ 取消 `analysis:read_assigned` → 保存。

让 B 刷新分析页 → 403；勾回保存 → B 刷新恢复。念一句："权限每请求重算，保存即生效，不用重启。"

### 6.3 限时角色（admin）

系统管理 → 用户与角色 → 选 `exec02` → 角色选「分析员」→ 到期时间填 2 分钟后 → 授予。

2 分钟后重登 exec02，该角色消失，访问分析接口 403。

### 6.4 在线状态与强制下线（admin）

系统管理 → 在线用户 → 看到四人在线 → 选 `exec01` 点「强制下线」→ A 继续操作返回 401；A 重新登录恢复。

### 6.5 账号与终端绑定（admin）

系统管理 → 设备绑定 → 选 `exec02` → 允许的 IP 填当前终端地址（如 `192.168.146.1`）→ 保存。

- 该终端登录成功；
- 换另一台终端登录 → 403「该账号已绑定终端」；
- 清空两项保存 → 恢复任意终端可登录。

### 6.6 AI 降级（可选，A 在 Ubuntu 上）

```bash
cd ~/NIS
sed -i 's/^AI_ENABLED=.*/AI_ENABLED=false/' .env && ./deploy/nis.sh up
```

再点「请求 AI 建议」→ 返回 503「AI 建议服务当前不可用，请人工完成该环节」，业务继续。

恢复：

```bash
sed -i 's/^AI_ENABLED=.*/AI_ENABLED=true/' .env && ./deploy/nis.sh up
```

## 7. 现场问答速答

| 可能被问 | 回答 |
|---|---|
| AI 跑在哪 | 服务端统一调用：A 的宿主机 Ollama（gemma3:4b），四类角色在自己终端都能用 |
| AI 会不会替人决策 | 不会。建议必须"接受/修改/舍弃"后才写入业务字段，且全程审计 |
| AI 建议为什么不一致 | 现在建议基于记录/报告原文生成（跨服务授权读取），不会凭空编 |
| 为什么报告显示"已决策" | 起草指令自动置 `研判中`，下达成功置 `已决策`；没有指令的报告仍是"待研判" |
| 一条指令多人执行 | 支持，每人一条个人分配；总体状态由决策侧按规则重算 |
| 并发修改怎么办 | 所有状态变更带 `expected_version`，旧版本返回 409 |
| 重复提交会不会重复 | 带 `Idempotency-Key`，重复提交返回原结果 |
| 权限是怎么判定的 | 每次请求把「该用户所有未过期角色的权限」取并集现算，改权限即时生效（白话见手册附录 G-3） |
| 总状态是谁算的 | 决策服务按规则统一重算（白话见手册附录 G-4） |
| AI 怎么知道记录内容 | 通过 `purpose=ai` 授权读取正文，拼进提示词；模型不可用回退模板（白话见手册附录 G-5） |

## 8. 快速兜底

| 现象 | 处理 |
|---|---|
| 「请求 AI 建议」按钮灰 | 必填项没填全，补齐标题/正文/来源类型/可信度 |
| AI 建议 5 秒内没出来 | 模型在排队或首次加载，等 10–15 秒；超时自动回退规则模板 |
| 提交时提示 409 | 页面数据过期（别人动过或你开了两个窗口），刷新后重做该步 |
| 提示"存在活动指令冲突" | 勾选「已确认冲突并继续」，向下达 |
| 时间不够 | 跳过第 6 节可选演示，只走第 1–5 节（约 4 分钟） |
