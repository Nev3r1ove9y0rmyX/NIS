# 协同调度信息系统需求规格说明书

版本：0.1（需求基线候选）

状态：待全组评审

负责人：A

## 1. 目标与范围

系统用于在课程授权的实验环境中支持侦察、分析、决策、执行四类人员协同工作，并通过中心数据库和审计日志形成可追溯的 OODA 信息闭环。

本阶段范围包括：身份认证、用户/角色/权限管理、组织结构、四类业务数据流转、每环节 AI 辅助与人工确认、操作审计、三域网络部署和验收测试。

本阶段不包括：真实生产指挥、对未授权目标的侦察或攻击、复杂微服务、移动客户端、高可用集群、计费和公网运营。

## 2. 参与者

| 参与者 | 职责 |
|---|---|
| 侦察员 | 采集、整理并提交侦察信息，选择目标分析员 |
| 分析员 | 阅读被指派的信息，形成分析报告，选择目标决策员 |
| 决策员 | 阅读报告，选择执行员并下达指令，查看执行结果 |
| 执行员 | 接收或拒绝指令，记录执行过程并提交结果 |
| 管理权限持有者 | 配置用户、组织、角色和权限；不是第五种业务角色 |
| AI 服务 | 为四个环节生成建议；不得替代人工确认和提交 |

一个用户可拥有多个角色，一个角色可分配给多个用户；角色与权限也是多对多关系。

## 3. 功能需求

### 3.1 身份、权限与组织

| 编号 | 优先级 | 需求与验收条件 |
|---|---:|---|
| FR-AUTH-001 | P0 | 用户以用户名和密码完成一次登录；合法账号成功，非法或停用账号失败；会话内业务操作不重复要求登录。 |
| FR-AUTH-002 | P0 | 登录后系统返回当前用户、组织和全部有效角色，前端正确显示。 |
| FR-AUTH-003 | P0 | 用户、角色、权限是独立实体；修改角色权限后，其关联用户按重新请求/刷新会话后的最新权限生效。 |
| FR-AUTH-004 | P0 | 用户与角色、角色与权限均支持多对多；多角色用户获得所属角色权限并集，但不能访问并集中不存在的资源。 |
| FR-AUTH-005 | P0 | 后端对每个受保护 API 验证身份、权限、资源范围和当前状态；无权限请求被拒绝并写审计。 |
| FR-ORG-001 | P0 | 系统保存组织单元和用户所属组织；管理权限持有者可配置组织与人员关系。 |
| FR-ORG-002 | P0 | 业务流转选择接收人时，仅返回目标角色、启用状态和组织规则均匹配的用户。 |

### 3.2 侦察环节

| 编号 | 优先级 | 需求与验收条件 |
|---|---:|---|
| FR-RECON-001 | P0 | 侦察员可创建和编辑本人草稿，至少填写标题、来源、内容、可信度和优先级。 |
| FR-RECON-002 | P0 | 侦察员可请求 AI 对信息进行摘要、分类或缺项提示；输出标为 AI 建议，只有人工确认后才写入业务字段。 |
| FR-RECON-003 | P0 | 提交前侦察员从合理候选列表中选择至少一名分析员；提交后数据持久化且普通侦察员不能任意改写。 |
| FR-RECON-004 | P0 | 侦察员可查看本人记录和处理状态；分析员只能查看指派给自己或按组织规则授权的记录。 |

### 3.3 分析环节

| 编号 | 优先级 | 需求与验收条件 |
|---|---:|---|
| FR-ANALYSIS-001 | P0 | 分析员可查看被指派侦察记录并创建分析报告，报告可关联一条或多条记录。 |
| FR-ANALYSIS-002 | P0 | 报告至少包括关键发现、关联关系、风险/优先级、建议手段和结论。 |
| FR-ANALYSIS-003 | P0 | 分析员可请求 AI 提取实体、关联、风险和建议；必须区分 AI 原始建议、人工修改内容和人工确认状态。 |
| FR-ANALYSIS-004 | P0 | 提交报告时选择合理的决策员；提交后报告持久化并进入待决策状态。 |
| FR-ANALYSIS-005 | P0 | 多分析员对相同侦察信息的报告独立保存，不自动覆盖；决策员可并列查看来源与作者。 |

### 3.4 决策环节

| 编号 | 优先级 | 需求与验收条件 |
|---|---:|---|
| FR-DECISION-001 | P0 | 决策员可查看指派给自己的分析报告及关联侦察依据。 |
| FR-DECISION-002 | P0 | 决策员可请求 AI 比较方案、提示冲突或生成指令草稿；最终目标、内容、接收人和下达动作由人确认。 |
| FR-DECISION-003 | P0 | 决策员可创建指令，至少填写标题、目标、内容、优先级、截止时间并选择一个或多个合理执行员。 |
| FR-DECISION-004 | P0 | 系统在下达前检查同一报告/目标上的活动指令并提示潜在冲突；用户必须确认或取消，重复请求不得产生重复指令。 |
| FR-DECISION-005 | P0 | 决策员可查看指令及每个接收人的执行状态和最终结果。 |

### 3.5 执行环节

| 编号 | 优先级 | 需求与验收条件 |
|---|---:|---|
| FR-EXEC-001 | P0 | 执行员只能查看分配给自己的指令，并可接收或填写理由拒绝。 |
| FR-EXEC-002 | P0 | 接收后可标记执行中，提交成功或失败结果；结果至少包括状态、说明和时间。 |
| FR-EXEC-003 | P0 | 执行员可请求 AI 生成步骤检查表、结果摘要或风险提示；实际执行确认和结果提交由人完成。 |
| FR-EXEC-004 | P0 | 重复接收、重复完成和非法状态转换被拒绝；一次网络重试不能生成重复结果。 |

### 3.6 日志、管理和扩展目标

| 编号 | 优先级 | 需求与验收条件 |
|---|---:|---|
| FR-AUDIT-001 | P0 | 登录、失败登录、敏感查询、创建、修改、提交、指派、状态转换、越权和系统关键事件都有日志。 |
| FR-AUDIT-002 | P0 | 日志包含操作者、当时角色、动作、对象、时间、来源 IP、请求追踪 ID、成功/失败及原因，且不记录密码或 Token。 |
| FR-AUDIT-003 | P0 | 授权用户能按业务对象或请求追踪 ID 还原完整 OODA 操作链。 |
| FR-ADMIN-001 | P0 | 管理权限持有者可查看并配置用户、角色、权限、组织关系和用户角色分配。 |
| FR-PRIORITY-001 | P1 | 任务支持普通、紧急优先级；紧急任务列表优先展示并同时以文字和醒目样式提示。 |
| FR-BACKUP-001 | P1 | 系统提供中心数据库备份和恢复流程，并至少完成一次实际恢复验证。 |

## 4. 状态与冲突规则

详细规则见 [业务状态机](workflow.md)。所有状态转换由后端原子校验；前端不得通过直接构造请求绕过规则。

- 同类多用户的数据使用“所有者 + 指派关系”区分。
- 多分析员报告并列存在，由决策员比较，不自动合并或覆盖。
- 多决策员发现活动指令冲突时必须收到冲突提示；完全相同的幂等请求只产生一次结果。
- 指令分配给多人时，每名执行员有独立接收和执行状态，指令总体状态由这些子状态汇总。
- 可编辑资源使用版本号进行乐观并发控制，旧版本更新返回冲突。

## 5. 非功能需求

| 编号 | 优先级 | 需求与验收条件 |
|---|---:|---|
| NFR-SEC-001 | P0 | 密码使用成熟自适应哈希保存；仓库和日志中无明文密码、Token、私钥。 |
| NFR-SEC-002 | P0 | 数据库无外网端口映射，只接受批准的 API 主机连接；DMZ 不能主动访问内网服务。 |
| NFR-SEC-003 | P0 | 所有输入由服务端验证，错误响应不泄露堆栈、SQL、密钥和内部路径。 |
| NFR-NET-001 | P0 | 外网、DMZ、内网使用不同网段；内网可访问外网和 DMZ 服务，外网仅访问公开 DMZ 服务。 |
| NFR-CONC-001 | P0 | 至少四台终端可以同时保持会话并完成各角色操作，不发生用户或数据串号。 |
| NFR-REL-001 | P0 | 数据库写入失败或事务异常时不产生半完成业务状态；客户端得到明确失败响应。 |
| NFR-AI-001 | P0 | AI 服务不可用、超时或结果被拒绝时，人工流程仍可继续；AI 输出记录来源和确认人。 |
| NFR-DEP-001 | P0 | 新环境依据仓库说明可启动系统、迁移数据库、创建演示数据并完成健康检查。 |
| NFR-MAINT-001 | P1 | 代码、接口、配置和测试通过 Git 与 PR 可追溯；关键技术变更使用 ADR。 |
| NFR-UX-001 | P1 | 支持常见桌面分辨率；加载、空数据、无权限、冲突和服务异常均有明确界面。 |

## 6. 统一业务字段基线

以下名称是前后端契约评审的起点：

- 角色代码：`reconnaissance`、`analyst`、`decision_maker`、`executor`；
- 优先级：`normal`、`urgent`；
- 人工确认：`human_confirmed` 布尔值、`confirmed_by`、`confirmed_at`；
- 并发控制：业务资源使用 `version` 整数；
- 通用审计字段：`created_at`、`created_by`、`updated_at`、`updated_by`；
- API 前缀：`/api/v1`。

字段最终以 B 提交并经 A/C/D 评审通过的 OpenAPI 为准。

## 7. 验收策略

需求与测试的映射见 [需求追踪矩阵](traceability.md)。P0 基础需求必须在中期验收前全部通过；P1 扩展需求不能阻塞 P0 闭环。
