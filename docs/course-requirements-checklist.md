# 课程要求核对表

本文是团队根据课程材料整理的原创摘要，用于项目执行和验收追踪，不替代课程原始文件。

## 一、必须满足的基础要求

| 编号 | 要求 | 验收证据 | 责任人 |
|---|---|---|---|
| CR-B01 | 部署中心数据库，保存侦察信息、分析报告、指令和执行结果 | 数据库记录、完整业务演示 | B、D |
| CR-B02 | 记录各类用户操作日志和关键系统日志 | 审计查询、系统日志、测试记录 | B、D |
| CR-B03 | 建立外网、信任内网和 DMZ 三个不同网段 | 拓扑、IP 配置、现场检查 | D |
| CR-B04 | 内网主机能够访问外网和 DMZ 业务服务 | 连通和 HTTP 测试 | D |
| CR-B05 | 外网主机能够访问 DMZ 公开服务 | 端口映射和 HTTP 测试 | D |
| CR-B06 | DMZ 主机不能访问内网主机服务 | 拒绝测试和防火墙日志 | D |
| CR-B07 | 存在侦察员、分析员、决策员、执行员四类标准角色 | 管理界面和数据库记录 | A、B、C |
| CR-B08 | 用户单次登录后被正确识别角色，不在业务流程中重复认证 | 四类账号演示 | B、C |
| CR-B09 | 后端实施基于角色和权限的访问控制，拦截页面、数据和 API 越权 | 四类账号越权测试 | B、C |
| CR-B10 | 用户、角色、权限三个实体分离，通过角色赋权 | 管理功能、数据模型、测试 | B、C |
| CR-B11 | 用户与角色、角色与权限均为多对多关系；多角色用户仍受正确控制 | 配置和功能测试 | B、C |
| CR-B12 | 完成侦察、分析、决策、执行的完整 OODA 闭环 | 真实接口和数据库演示 | 全员 |
| CR-B13 | OODA 每个环节均有 AI 辅助且关键动作由人确认 | AI 建议和人工确认演示 | A、B、C |
| CR-B14 | 每类角色支持多名用户，流转时可以选择具体目标用户 | 多用户并行测试 | A、B、C |
| CR-B15 | 存在组织结构，候选接收人只显示业务上合理的用户 | 组织和候选人筛选测试 | A、B、C |

基础要求必须在第 8 次课结束前全部通过，作为当前开发的 P0 范围。

## 二、选定的第一批扩展目标

| 编号 | 目标 | 优先级 | 选择理由 |
|---|---|---:|---|
| CR-E01 | 采用需求、架构、接口、测试、版本管理、看板和评审等软件工程方法 | P1 | 当前仓库已具备基础，增量成本低且证据清晰 |
| CR-E02 | 数据安全：密码安全存储、访问限制、传输保护、备份恢复、高危操作审计 | P1 | 与系统安全和部署直接相关 |
| CR-E03 | 普通/紧急任务优先级、紧急标红和优先排序 | P1 | 对状态和 UI 改动较小，容易稳定验收 |

## 三、暂缓的扩展目标

以下目标先进入 P2 Backlog。只有 P0 全部联调通过后才进入开发，避免扩展功能拖累基础验收：

- 更细粒度的可配置功能权限；
- 限时角色和临时权限自动回收；
- 用户在线状态和强制下线；
- 账号与 IP/MAC 绑定；
- 未完成任务转交。

## 四、团队可自行决定的内容

- 具体前后端框架和数据库产品；
- 系统逻辑模块和页面布局；
- 物理机、虚拟机和容器的组合；
- 外网、内网、DMZ 的具体地址段；
- AI 服务的具体模型和部署方式；
- 多分析员结论冲突及多决策员指令冲突的具体解决规则。

团队选择必须满足基础要求并留下设计、配置和测试证据。

## 五、当前明确假设

1. 基础验收优先于扩展目标，P0 未通过时不并行开发高风险扩展功能。
2. 为满足“DMZ 主机无法访问内网主机服务”，应用 API 与中心数据库均部署在 DMZ 的服务侧，数据库仅允许 API 主机访问且不做外网端口映射。若教师现场对“中心数据库位置”另有明确要求，需通过变更 Issue 调整拓扑。
3. 四台成员电脑在开发期不必同网；联调和验收期接入同一受控内网。
4. AI 功能允许调用本地或远程模型；模型不可用时不得阻断人工业务闭环。
5. 附件第一阶段仅保存文件元数据和受控文件引用，不把大文件或敏感原始数据提交 Git。

## 六、尚待团队/教师确认

- 现场外网的地址获取方式、是否允许自带路由器/交换机；
- AI 服务是否必须完全离线；
- “系统日志”的最低事件范围和保留时间；
- 是否要求独立管理角色；本设计暂由具有管理权限的多角色用户承担配置工作，不新增第五种业务角色；
- 最终分组编号、四人姓名、学号和具体日期。
