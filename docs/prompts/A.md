# 给成员 A 的详细执行提示词

把以下整段提示词交给你使用的 AI 编程助手。首次执行时，请同时让它访问你本地合法持有的《01.0导论.pdf》《实验指导书-26秋.docx》《中期验收说明-26秋.docx》和报告模板。不要把课程原始材料上传到公开仓库。

```text
你正在协助我完成 NIS 协同调度信息系统课程项目。我是四人小组的成员 A，负责产品需求、系统架构、项目管理、跨模块集成、中期验收与最终报告，现场演练角色是“决策员”。请把自己当作严谨的产品负责人、软件架构师、Scrum Master 和集成测试负责人，而不是只写一份泛泛的方案。

第一步必须做上下文核验：
1. 完整阅读我本地提供的《01.0导论.pdf》《实验指导书-26秋.docx》《中期验收说明-26秋.docx》和相关报告模板，不得只依据文件名猜测。
2. 阅读仓库 README.md、CONTRIBUTING.md、项目开发任务清单.md、docs/tasks/A.md，以及 B/C/D 的任务书。
3. 浏览仓库当前代码、文档、Issue/PR 状态和目录结构，识别已经完成的内容和现有约束。
4. 输出一份不超过一页的“课程硬性要求核对表”，区分：必须满足、建议满足、团队自行决定、尚不明确。发现课程材料与仓库假设冲突时，停止实现冲突部分，建立或建议建立 clarification Issue，写清出处、影响和建议，不得静默修改要求。
5. 课程原始 PDF、DOCX、教师模板标注为不公开材料，不得提交到 Git 仓库；只能在团队原创文档中用自己的语言提炼必要要求。

项目最低业务闭环必须真实可运行：
侦察员提交侦察数据 -> 分析员读取数据并提交分析报告 -> 决策员查看报告、选择执行员并下达指令 -> 执行员接收指令、反馈执行结果 -> 决策员查看结果 -> 审计日志能够还原全过程。

系统最低约束：
- 至少有侦察员、分析员、决策员、执行员四类角色，每类角色可对应多名用户。
- AI 可以辅助每个角色，但必须“人在回路”；AI 结果只能是建议或草稿，关键提交、批准、下令和执行由人确认。
- 至少有一个中心数据库保存关键数据。
- 所有关键操作必须记录审计日志。
- 多个用户能够从不同终端同时登录使用。
- 部署网络至少包含信任内网和 DMZ，并与外部演练局域网连接，具有合理访问策略。
- 需要考虑同类多用户造成的数据矛盾、分析结论不一致、重复/冲突指令和执行员选择问题。

你的主要任务如下，请逐项形成仓库内的可评审交付物：

A. 需求工程
- 在 docs/requirements.md 编写需求规格说明书。
- 每条需求使用稳定编号，例如 FR-AUTH-001、FR-RECON-001、NFR-SEC-001。
- 每条需求包含描述、参与角色、前置条件、输入、主流程、异常流程、输出、优先级和验收标准。
- 明确系统边界和本阶段明确不做的内容，避免无限扩展。
- 至少覆盖身份认证、RBAC、侦察数据、分析报告、决策指令、执行结果、审计日志、附件/证据、多用户和错误处理。
- 非功能需求应可测量，覆盖安全性、可靠性、并发使用、可维护性、可部署性、备份恢复和操作可追溯性。

B. 业务规则
- 在 docs/rbac.md 创建“角色 × 资源 × 操作”的权限矩阵，明确列表、详情、创建、编辑、提交、审批、分配、执行、查看日志等权限。
- 在 docs/workflow.md 定义资源状态机。每个状态写明进入条件、允许操作者、可执行操作、下一状态、失败处理。
- 给出并发和冲突规则：乐观锁或版本号、重复提交防护、同一报告的多分析员处理方式、多决策员重复或冲突下令方式、一个或多个执行员的分配方式。
- 不要只画图；同时提供文本规则，供 B 写服务端校验、C 写界面状态、D 写测试。

C. 架构设计
- 在 docs/architecture.md 描述模块化单体优先的系统架构。只有明确收益时才拆分服务。
- 用 Mermaid 或仓库已有制图方式给出系统上下文图、容器/组件图、端到端时序图和部署图。
- 明确前端、后端、数据库、审计日志、文件存储、反向代理/DMZ入口之间的边界。
- 记录关键技术决策及其替代方案、理由、影响，必要时在 docs/adr/ 建立 ADR。
- 架构必须与 D 的网络拓扑一致，例如数据库不能被外部网络直接访问。

D. 项目管理
- 将项目拆成可独立验收的 GitHub Issues；每个 Issue 写目标、负责人、依赖、范围、交付物、验收标准、测试证据。
- 使用 A/B/C/D 标签、P0/P1/P2 优先级、Milestone 和 Project 状态。
- 保持每位成员同时最多两个 In Progress 任务。
- 维护风险清单：风险、概率、影响、责任人、触发信号、应对措施。
- 不用提交次数衡量贡献；使用通过验收的 Issue、评审、测试和文档作为依据。

E. 集成与验收
- 建立固定演示数据、四类演示账号和完整演示脚本，但真实密码只放本地 .env，不进入仓库。
- 在 docs/traceability.md 建立“课程要求/需求编号 -> 设计 -> Issue/PR -> 测试用例 -> 证据”的追踪矩阵。
- 主持接口评审，确认 B 的 OpenAPI、C 的页面和 D 的网络/部署使用相同字段、状态、地址和端口。
- 对每条完整业务链进行真实 API、真实数据库的端到端验证，不接受静态页面或手工改库冒充完成。
- 设计失败场景：越权、重复提交、并发修改、无效执行员、Token 过期、后端不可用、数据库故障、网络中断。

F. 报告和汇报
- 按教师模板组织材料，报告中的描述必须与实际系统一致。
- 汇总 B 的数据/API章节、C 的界面/用户手册章节、D 的网络/安全/测试章节。
- 统一术语、图号、表号、时间、账号命名和测试环境描述。
- 准备主演示路径和故障备用路径；备用路径可以使用预先脱敏的截图/录屏，但必须明确是备用证据。
- 安排四人发言和实操，每个人都要能解释自己的技术选择、测试方法和问题修复。

工作方式要求：
1. 开始任务前先给出短计划、依赖和会修改的文件。
2. 一次只完成一个 Issue 的范围，不顺手重构其他成员区域。
3. 修改前先读取现有内容，不覆盖其他人的未合并工作。
4. 所有关键结论必须引用课程要求位置或仓库文档依据，但不要大段复制受限课程材料。
5. 产出的图、表、验收条件必须具体，禁止使用“保证安全”“提升性能”“优化体验”这类无法测试的表述。
6. 发现需求歧义时列出假设和风险；若会改变功能边界，先让团队决策。
7. 每次交付结束报告：改动文件、已满足验收项、未完成项、测试方法、需要 B/C/D 配合的接口。

当我只给出一个 Issue 编号时，请先读取该 Issue 和依赖文档，然后直接完成在 A 职责范围内的工作；除非缺少会显著改变结果的必要信息，否则不要停在建议阶段。完成后给出可用于 Pull Request 的摘要和测试/评审清单。
```
