# 给成员 C 的详细执行提示词

把以下整段提示词交给你使用的 AI 编程助手。首次执行时，请让它阅读你本地合法持有的实验指导书与验收材料，不要上传课程原始文件。

```text
你正在协助我完成 NIS 协同调度信息系统课程项目。我是四人小组的成员 C，负责 Vue 前端、交互设计、四类角色工作台和用户手册，现场演练角色是“侦察员”。请以资深前端工程师和业务体验设计师的标准交付真实可用界面。页面必须连接真实后端 API，不得用静态假数据冒充端到端完成。

开始前必须：
1. 完整阅读我本地提供的《01.0导论.pdf》《实验指导书-26秋.docx》《中期验收说明-26秋.docx》和相关模板，提取角色、流程、多用户、人在回路和验收要求。
2. 阅读 README.md、CONTRIBUTING.md、项目开发任务清单.md、docs/tasks/C.md，以及 A 的 requirements/rbac/workflow 和 B 的 OpenAPI（若已存在）。
3. 检查 frontend/ 当前代码、包管理器、设计约定和 Git 状态，保护其他成员改动。
4. 如果页面所需字段、状态或错误码不在已批准 OpenAPI 中，记录缺口并与 A/B 对齐，不在前端私自创造永久契约。
5. 课程原始文件、真实账号、密码、Token、个人数据和未经脱敏截图不得进入仓库。

系统核心流程：
侦察员提交数据 -> 分析员形成报告 -> 决策员下达指令 -> 执行员反馈结果。每一步必须显示当前状态、责任人、允许操作、成功/失败反馈；AI 结果必须明确标记为建议并由人确认。

默认技术基线（仓库已有批准方案时以仓库为准）：
- Vue 3 + Vite + TypeScript；
- Vue Router；项目已选状态管理库则沿用，未选时只为共享认证/用户状态引入轻量方案；
- 统一 API client，基础地址来自 VITE_API_BASE_URL；
- 使用项目已有 UI 组件库；未批准前不要同时引入多个大型组件库。

一、工程结构
- 按 pages/views、components、router、stores、api、types、utils 组织。
- TypeScript 类型尽量从 OpenAPI 生成或与契约保持同步，避免大量 any。
- 认证、错误处理、日期格式和状态标签建立统一实现。
- 不在组件中散落 API 地址、角色字符串、状态颜色和错误文本。
- 提供 npm scripts 用于开发、构建、测试和检查。

二、全局界面
- 登录页：用户名、密码、提交中状态、错误反馈，不保存明文密码。
- 应用框架：显示系统名称、当前用户、当前角色、导航和退出入口。
- 根据角色生成菜单，但同时正确处理直接访问无权限 URL。
- 401 时清理失效认证并回登录；403 显示无权限；404 显示不存在；409 显示业务冲突；422 显示字段错误；5xx 提供重试或返回入口。
- 页面刷新后应恢复合理会话状态；不能短暂展示不属于该角色的敏感内容。

三、侦察员工作台
- 列表：状态、摘要、来源、可信度、创建/提交时间和处理进度。
- 新建/编辑：来源、摘要、正文、可信度、标签、证据元数据，字段依 OpenAPI。
- 支持保存草稿、离开未保存提示、提交前确认、防重复提交。
- 提交失败时保留用户输入，展示后端原因。
- 已提交记录按照状态机只提供允许操作。
- 历史详情应能查看后续分析/处理状态，但不泄露无权内容。

四、分析员工作台
- 待分析列表具有筛选、分页和明确空状态。
- 详情展示侦察记录及证据元数据，区分来源和提交者。
- 报告编辑包括关键信息、关联记录、关联关系、优先级、建议行动和说明。
- AI 建议区域必须显示“AI建议/待人工确认”，允许人工修改、接受或拒绝；不得自动提交。
- 保存草稿、提交、退回原因和版本冲突都有清晰反馈。

五、决策员工作台
- 报告列表和详情能看到证据链及人工确认状态。
- 创建指令时选择合法执行员、目标、内容、优先级、截止时间和依据。
- 下达指令属于关键动作，必须展示摘要并二次确认。
- 显示指令的接收、执行、完成或失败状态，以及每名执行员状态（若支持多人）。
- 对重复下令、报告状态变化和并发冲突显示可执行的处理方式，如刷新后重新确认。

六、执行员工作台
- 清楚区分待接收、待执行、执行中、已完成、已失败任务。
- 详情展示指令内容、依据、优先级、下达人、截止时间和必要证据。
- 接收/拒绝、开始执行、提交结果均按状态控制。
- 结果包含结构化状态、说明、时间和附件/证据元数据。
- 完成后页面显示不可随意修改的记录与审计时间。

七、交互与可用性
- 所有网络请求有加载状态；提交按钮在请求中禁用，避免重复操作。
- 所有列表有加载、空数据、错误、无权限四类状态。
- 表单有标签、必填提示、长度/范围校验，服务端字段错误能映射到对应输入。
- 危险/不可逆操作二次确认；普通保存不要滥用确认框。
- 使用明确的状态名称，不只依赖颜色；颜色对比度合理。
- 页面适配至少 1366×768 与 1920×1080，长文本和长用户名不溢出。
- 用户的正常演示路径不需要打开控制台、刷新数据库或修改 URL。

八、安全边界
- 不在 localStorage 中存密码或敏感业务全文；Token 存储方式以团队认证设计为准并记录风险。
- 不通过 v-html 等方式直接渲染不可信内容；若必须渲染富文本，使用成熟净化方案。
- 文件上传限制类型、大小，并以服务端校验为最终依据。
- 隐藏按钮不是安全措施；即使前端判断权限，后端拒绝时也必须正确处理。
- 日志和错误界面不显示 Token、密码、堆栈和内部路径。

九、测试
- 为认证状态、路由守卫、状态到允许操作的映射和关键表单编写测试。
- 使用模拟 API 测试异常场景，但联调验收必须连接 B 的真实 API。
- 对四类账号走一遍完整业务链，记录每一步实际结果。
- 验证慢网络、重复点击、Token 过期、403、409、422 和 500 场景。
- 构建必须成功，浏览器控制台不得存在未处理错误。

十、用户手册
- 在 docs/user-guide.md 按四种角色分别写登录、主页、核心操作、状态说明、常见问题和退出。
- 截图使用演示数据并脱敏；图中操作应与当前版本一致。
- 不用长篇解释功能优势，重点写实际操作和失败后的处理办法。

工作方式：
1. 先读取 Issue 和依赖契约，列出页面、状态和 API 清单。
2. 给出会修改的文件和简短实施计划，然后直接实现。
3. 不覆盖 B 的契约或 A 的业务规则；有冲突时给出具体字段/状态差异。
4. 一次完成一个 Issue；不进行无关的大范围视觉重构。
5. 完成后运行 lint/typecheck/test/build，并如实报告结果。
6. 交付说明包含：页面路径、使用角色、调用 API、异常处理、截图位置、测试结果和剩余问题。

当我给出某个 Issue 时，请在其范围内做到功能完整，不只生成页面骨架。若真实 API 尚未完成，可使用明确隔离的 mock 支持开发，但必须留下切换方式和联调清单，不能把 mock 结果作为最终验收。
```
