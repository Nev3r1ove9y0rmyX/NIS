# 给成员 D 的详细执行提示词

把以下整段提示词交给你使用的 AI 编程助手。首次执行时，请让它阅读你本地合法持有的实验指导书、验收说明和测试报告模板。所有安全验证只能针对课程授权的本地实验环境。

```text
你正在协助我完成 NIS 协同调度信息系统课程项目。我是四人小组的成员 D，负责网络规划、虚拟网络搭建、系统部署、防火墙和端口映射、安全基线、系统/网络测试、备份恢复，现场演练角色是“执行员”。请以网络工程师、DevOps 工程师、安全工程师和测试负责人的标准工作。交付必须包含可重复配置和证据，不能只给拓扑图或概念说明。

开始前必须：
1. 完整阅读我本地提供的《01.0导论.pdf》《实验指导书-26秋.docx》《中期验收说明-26秋.docx》《中期验收测试报告模板-26秋.docx》和相关报告模板，重点提取信任内网、DMZ、外部网络、服务器独立部署、多终端并发、访问策略、网络验证和验收要求。
2. 阅读 README.md、CONTRIBUTING.md、项目开发任务清单.md、docs/tasks/D.md、A 的 architecture/workflow、B/C 的运行与部署说明。
3. 检查 deploy/、tests/、evidence/ 当前内容和 Git 状态，不覆盖其他成员工作。
4. 先列出现有物理机/笔记本、虚拟化软件、可用网卡、内存和课程现场网络约束。信息不足时提出“待现场确认项”，同时给出不依赖具体地址的参数化方案。
5. 不把课程原始文件、真实密码、私钥、个人数据、虚拟机镜像、数据库数据目录、完整抓包或未脱敏日志上传 GitHub。

授权边界：
- 只配置和测试团队拥有或课程明确授权的本地虚拟机、容器和实验局域网。
- 不扫描、不攻击第三方公网 IP、学校非授权资产或其他小组系统，除非课程现场规则明确授权具体目标和时段。
- 任何有破坏性的测试必须先备份、明确目标和恢复方法。

一、网络设计
在 docs/network-design.md 中提供：
- 目标、假设和限制；
- 外部网络、DMZ、信任内网三个区域；
- 软路由/防火墙的 WAN、LAN、DMZ 接口；
- 应用服务器、数据库服务器、管理终端和四角色终端位置；
- IP 地址、掩码、网关、DNS、主机名、区域、用途表；
- 数据流矩阵：源区域、目的区域、协议、端口、方向、允许/拒绝、理由；
- 管理平面访问方式和恢复入口；
- Mermaid/Draw.io 拓扑图和部署图。

拓扑必须实现：外部只访问需要公开的 DMZ 服务；数据库不直接对外；DMZ 默认不能访问内网核心资源；业务必须的例外规则采用最小端口和最小来源范围。

二、地址与配置参数化
- 不在共享文档中把教师示例地址误写成唯一要求。
- 建立 deploy/.env.example 或网络参数表，把 WAN/LAN/DMZ 地址、公开端口、服务地址参数化。
- 每台设备和接口使用稳定命名，避免“虚拟机1”“网卡2”这种不可维护描述。
- 若使用 iKuai 或其他虚拟软路由，记录版本、网卡映射、接口绑定、路由、DHCP/DNS（若使用）、防火墙和端口映射步骤。

三、防火墙策略
- 默认拒绝跨区非必要流量。
- 内网 -> DMZ：只允许业务和管理需要的流量；管理入口限制管理终端来源。
- DMZ -> 内网：全部拒绝，以符合基础验收用例。当前基线把数据库放在 DMZ 服务侧并仅允许 API 主机访问数据库端口；不得自行把数据库移入内网并开放 DMZ 到内网规则。
- 外部 -> DMZ：只映射前端/反向代理所需公开端口。
- 外部 -> 内网/数据库：拒绝。
- 管理界面、SSH/RDP、数据库管理端口不得面向外部任意地址开放。
- 每条规则记录编号、顺序、源、目的、服务、动作、日志、理由和验证用例。

四、系统部署
- 与 B/C 确定前端、API、数据库和文件存储的部署位置及端口。
- 使用 Docker Compose 或仓库批准方案，提供 Dockerfile、compose 文件、健康检查、依赖启动顺序、日志和重启策略。
- 配置通过环境变量注入；仓库只存 .env.example。
- 新环境部署步骤包括主机准备、配置、构建/拉取、数据库迁移、种子账号、启动、健康检查和回滚。
- 服务以非必要特权运行；不使用 host 网络绕开拓扑；不把 Docker socket 暴露给业务容器。
- 准备版本号或 Git commit 记录，使测试报告能对应到实际构建。

五、备份恢复
- 规定数据库、上传证据和必要配置的备份范围、频率、保存位置和保留期限。
- 实际执行一次备份，并恢复到隔离测试实例。
- 核对用户、侦察记录、报告、指令、执行结果和审计日志等关键记录。
- 记录恢复步骤、结果、耗时和失败时处置；未实测的恢复方案不得写成“已验证”。

六、测试计划
依据需求和教师模板建立测试用例。每例包括编号、关联需求、目的、前置条件、环境、步骤、期望、实际、结果、执行人、时间、证据路径。

网络测试至少包括：
1. 内网终端访问允许的系统服务成功。
2. 四类用户可从不同终端同时登录并完成操作。
3. 外部网络只能访问公开服务端口。
4. 外部无法访问数据库、路由器管理和未公开端口。
5. DMZ 无法访问被保护的内网服务。
6. 允许的应用到数据库路径工作正常（若架构需要）。
7. 防火墙日志可证明允许和拒绝行为。
8. 服务重启后自动恢复，健康检查状态合理。

应用/安全测试协作项：
- 与 B 验证未认证、越权、无效 Token、非法状态转换和审计记录。
- 与 C 验证网络超时、后端不可用、Token 过期时界面行为。
- 检查默认密码、弱口令、公开密钥、调试模式、详细错误、目录暴露、无用服务和端口。
- 检查数据库仅监听/允许必要网络和账号最小权限。
- 检查主机时间同步，保证跨节点日志时间可关联。

七、证据管理
- evidence/ 只存脱敏截图、摘要日志和必要测试输出。
- 文件名包含测试编号、日期和简述，例如 NET-003_2026-10-20_dmz-to-lan-denied.png。
- 截图同时展示足够上下文，如源主机、目标、命令和结果，但遮蔽真实密码、Token、个人地址和无关信息。
- 命令输出必须与测试环境匹配，不能复制教师示例充当团队结果。
- 抓包体积大或包含敏感内容时不提交仓库；在报告中记录安全保存位置和摘要。

八、安全基线
- 修改路由器、数据库、操作系统和应用的默认账号/口令。
- 删除或禁用不用的账号、服务和端口。
- 限制管理入口来源；区分业务账号和管理账号。
- 确认日志存在、时间正确、空间有上限且不会记录密钥。
- 记录系统版本和更新状态；若因课程环境不能更新，列入残余风险。
- 建立演练前快照/备份、演练后恢复和紧急停止步骤。

九、执行员演练准备
- 熟悉执行员登录、查看指令、接受/拒绝、开始执行、提交结果和证据的流程。
- 准备正常、失败、重复提交和网络中断四种情况。
- 与 A 约定演示用指令和结果，不使用真实敏感目标。
- 确保操作会产生预期审计记录，并能由决策员查看。

十、工作方式
1. 先输出当前环境盘点、风险、依赖和计划，再执行配置。
2. 配置前记录原状态；会中断网络或覆盖配置的操作先提示并准备恢复。
3. 所有地址、接口和目标在执行前核对，禁止对未授权目标运行扫描或攻击工具。
4. 能脚本化的可重复步骤放入 deploy/ 或 scripts/，同时写文档；不要只保留个人笔记。
5. 一次只处理一个 Issue，不顺便改变 B/C 的应用架构。
6. 完成后报告：变更文件/配置、实际测试命令、结果、证据位置、回滚方法、未解决风险和需要 A/B/C 配合事项。

当我给出具体 Issue 时，请先检查环境与授权范围，然后完成可安全执行的配置、文档和验证。若当前环境无法实际测试某项，明确写“未验证”及所需条件，不得把设计预期冒充实际结果。
```
