# 给成员 B 的详细执行提示词

把以下整段提示词交给你使用的 AI 编程助手。首次执行时，请同时让它访问你本地合法持有的实验指导书和验收材料，但不得提交原始课程文件。

```text
你正在协助我完成 NIS 协同调度信息系统课程项目。我是四人小组的成员 B，负责后端、中心数据库、API、认证授权、业务状态校验和审计日志，现场演练角色是“分析员”。请以资深后端工程师、数据库设计师和应用安全工程师的标准工作，交付可运行、可测试、可部署的代码，不要只写示例或伪代码。

开始任何编码前必须：
1. 完整阅读我本地提供的《01.0导论.pdf》《实验指导书-26秋.docx》《中期验收说明-26秋.docx》及相关模板，提取与后端、数据库、多用户、日志、网络部署和验收相关的硬性要求。
2. 阅读 README.md、CONTRIBUTING.md、项目开发任务清单.md、docs/tasks/B.md，以及 A 的 requirements/rbac/workflow/architecture 文档（若已存在）。
3. 检查 backend/、deploy/、tests/ 的实际代码和当前 Git 状态，保留其他成员已有改动。
4. 如果 A 的权限矩阵、状态机或字段定义缺失/矛盾，先列出最小阻塞点并建立 Issue；不自行创造会影响 C 和 D 的协议。对不影响接口契约的实现细节可作保守选择并记录。
5. 不得把课程原始材料、真实密码、Token、私钥、个人数据、数据库数据目录或未脱敏日志提交到仓库。

项目业务链：
侦察数据 -> 分析报告 -> 决策指令 -> 执行结果，并对每一步记录审计信息。四类角色可有多名用户，AI 只能给出待人工确认的建议。

默认技术基线（如仓库已有不同且已批准的 ADR，以仓库为准）：
- Python 3.12；FastAPI；Pydantic v2；SQLAlchemy 2；Alembic；MySQL 8；pytest。
- REST JSON API，前缀 /api/v1。
- JWT 访问令牌和服务端 RBAC；密码使用成熟自适应哈希库。
- Docker Compose 供本地和实验环境部署。

一、工程结构与质量
- 建立清晰分层：api/routes、schemas、models、services、repositories（仅在确有价值时）、core/config/security、tests。
- 配置从环境变量读取，并提供无密钥的 .env.example。
- 提供应用健康检查。存活检查与就绪检查应能区分应用运行和数据库不可用。
- 统一错误响应，例如 {"code":"WORKFLOW_CONFLICT","message":"...","request_id":"..."}，禁止把堆栈、SQL、文件路径或密钥返回客户端。
- 采用格式化、静态检查和 pytest；新增功能必须新增或更新测试。

二、数据模型
至少实现并合理关联：
- User：用户名、显示名、密码哈希、启用状态、创建时间；
- Role 或稳定角色枚举；
- ReconRecord：创建者、来源、摘要、正文、可信度、标签、状态、版本；
- Evidence：关联对象、文件元数据或安全引用，不在日志暴露敏感内容；
- AnalysisReport：分析员、关联侦察记录、关键信息、关系、优先级、建议、AI草稿、人工确认、状态、版本；
- Command：决策员、依据报告、目标、内容、优先级、截止时间、状态；
- CommandAssignee：指令与一个或多个执行员的关系及个人执行状态；
- ExecutionResult：执行员、指令、结果、状态、说明、时间；
- AuditLog：操作者、角色、动作、资源、资源ID、来源IP、request_id、结果、失败原因、时间。

具体字段以已批准文档为准。必须有外键、唯一约束、必要索引、created_at/updated_at；重要业务数据使用状态或软删除，避免无审计的物理删除。时间在数据库/API 中使用一致时区策略。使用 Alembic 管理迁移，不能依赖应用启动时粗暴重建表。

三、认证授权
- 实现登录、当前用户、Token 验证和安全退出/失效策略。
- 密码绝不明文保存或记录；使用成熟密码哈希实现，不自创加密算法。
- 每个受保护 API 在后端验证角色、资源所有权、分配关系和当前状态。
- 401 用于未认证，403 用于已认证但无权限，404 避免泄露不应可见资源时按团队规则处理。
- 失败登录、无效令牌、越权尝试进入安全审计。
- 创建四类演示账号的种子脚本，默认密码来自环境变量或首次运行配置，不写死真实密码。

四、业务 API
侦察记录：创建草稿、修改自己的草稿、提交、分页列表、详情；提交后按状态机限制修改。
分析报告：读取允许的侦察记录，创建报告，关联多条记录，保存分析和优先级，保存 AI 建议但标记来源，人工确认后提交，支持按规则退回。
决策指令：决策员基于报告创建、选择合法执行员、下达、查询、按规则撤回；拒绝重复或冲突指令。
执行结果：被指派执行员查询、接收/拒绝、开始、提交成功或失败结果、附加证据；拒绝非法和重复状态转换。
审计查询：仅授权用户按操作者、资源、时间、结果筛选，分页返回；审计记录本身不可由普通业务接口修改。

五、并发与一致性
- 对容易并发编辑的业务对象使用版本号/乐观锁或团队批准的等价方案。
- 状态检查和写入在同一事务中完成。
- 防止按钮重复点击、网络重试造成重复提交，可采用唯一业务键、幂等键或严格状态转换。
- 数据库异常时正确回滚，不产生“指令已下达但接收人未建立”之类半完成状态。
- 为冲突返回稳定的 409 错误码，让 C 能提供明确提示。

六、审计要求
- 登录、退出、敏感查询、创建、编辑、提交、审批、下令、接收、执行、失败操作都写审计日志。
- 审计至少包含 who/when/where/what/result/request_id。
- 不记录密码、Token、完整请求头、文件内容或无必要的敏感正文。
- 明确审计写入失败策略；关键业务不能在完全无审计的情况下静默成功。
- 提供一条可以按 request_id 或业务对象还原完整闭环的查询路径。

七、API 契约
- OpenAPI 中补全 tag、摘要、Schema、枚举、成功响应和常见错误响应。
- 列表接口有 page/page_size 或批准的分页方式，并限制最大页大小。
- 输入进行类型、长度、范围、格式和枚举校验。
- 字段命名、状态值和错误码不得与 C 私下另起一套；任何破坏性变更先更新契约并通知 A/C/D。

八、测试
每个模块至少测试：成功路径、未认证、越权、对象不存在、非法参数、非法状态转换、重复提交和并发冲突。
必须有一个集成测试贯穿完整业务链，并验证审计日志存在。
测试应独立、可重复，不依赖执行顺序；使用测试数据库或事务隔离，不连接个人生产数据。
为 D 提供健康检查、迁移、初始化、备份恢复所需接口和命令。

九、交付节奏
1. 先报告你理解的 Issue 范围、依赖和验收条件。
2. 阅读现有代码后再编辑；不要覆盖其他成员改动。
3. 使用小而可审查的提交，不把多个无关任务塞进同一个 PR。
4. 运行格式检查、静态检查、迁移测试和 pytest；报告真实结果，不能声称未运行的测试已通过。
5. 结束时提供：改动文件、数据库迁移说明、API变化、测试命令和结果、部署注意事项、需要 C 联调的示例、剩余风险。

当我给出具体 Issue 时，直接在其范围内完成实现和测试。若仓库尚为空，先完成最小可运行骨架和当前 Issue，不要一次性凭空写完整系统。任何安全测试仅针对课程授权的本地实验环境。
```
