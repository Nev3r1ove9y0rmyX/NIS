# 用户、角色、权限与组织规则

版本：0.1（基线候选）

## 1. 模型

系统采用权限驱动的 RBAC：

```text
User --< UserRole >-- Role --< RolePermission >-- Permission
  |
  +-- belongs to --> OrganizationUnit
```

- 用户与角色多对多；角色与权限多对多。
- 权限绑定到角色，不为单个用户硬编码业务权限。
- 一个多角色用户的有效权限是全部有效角色权限的并集，同时仍受资源所有权、组织范围、指派关系和资源状态约束。
- “管理”是一组权限，可授予具有一个或多个标准业务角色的指定用户，不新增第五种业务角色。
- 权限变更必须写审计；后端是最终授权判断者。

## 4. 资源范围规则

拥有权限代码仍需同时满足下列规则：

1. 草稿只能由创建者编辑，管理权限不默认包含改写业务内容。
2. 提交后的资源不可按普通编辑接口更改；后续修改需进入明确的退回或新版本流程。
3. 分析员只能读取明确指派给自己、指派给其组织范围或已由业务规则授权的侦察记录。
4. 决策员只能读取明确指派给自己的报告，以及报告引用的必要侦察依据。
5. 执行员只能读取分配给自己的指令；多人指令中不得看到其他执行员不必要的私有结果。
6. 决策员可查看本人相关指令的各接收人状态和结果。
7. 候选接收人必须同时满足：账号启用、目标角色有效、组织规则匹配、未超过权限有效期（若未来实现）。
8. 任何直接使用资源 ID 的请求都必须重新检查范围，不能依赖列表页面隐藏。

## 5. 多角色会话规则

- 用户一次登录后获得全部有效角色和权限，不重复认证。
- 前端显示当前工作上下文并允许在所属角色间切换；切换只改变工作台和默认筛选，不创造新权限。
- API 记录本次操作采用的角色上下文；该上下文必须属于用户有效角色。
- 后端按用户有效权限、角色上下文、资源范围和状态共同决策。
- 若同一用户既是上游又是下游角色，第一阶段允许其完成演示，但审计必须显示角色上下文；正式测试优先使用不同账号体现职责分离。

## 6. 授权决策顺序

```text
身份有效？
  -> 账号启用？
  -> 角色上下文属于该用户且有效？
  -> 角色拥有所需权限？
  -> 资源处于允许状态？
  -> 用户满足所有权/指派/组织范围？
  -> 允许，并记录审计
否则拒绝，并记录必要的安全审计
```

## 7. 验收场景

1. 一个角色关联两名用户，两人继承一致权限。
2. 一个用户同时拥有分析员和决策员角色，可切换工作台并完成两个角色的合法操作。
3. 多角色用户访问不属于任何所属角色的执行员 API，返回 403。
4. 侦察员修改角色无权访问的分析报告，返回 403 或防资源泄露规则规定的 404。
5. 执行员访问分配给另一人的指令，访问被拒绝。
6. 修改角色权限后，关联用户的后续授权结果同步变化。
7. 禁用用户后，其新请求和重新登录失败；现有 Token 的失效策略由 B 在安全设计中明确。
